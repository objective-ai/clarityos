## Summary

Phase 10.2 is a pure frontend revamp — no backend logic changes. The appointment data model, all BFF routes, and the public booking backend are already complete. The work is entirely UI: five new/redesigned components (WeekStrip, AppointmentDetailDrawer, BookingDrawer, FlowBoard, WeekView) plus an upgrade to the existing public booking wizard at `app/book/[slug]/page.tsx`.

The existing codebase provides strong foundations: `TimelineView` already implements the time-slot grid that week view will extend; `ClinicView` provides the multi-column pattern; `AppointmentCard` has the action architecture that cards across all views will share; `BookAppointmentModal` has patient search and conflict detection logic that the new drawer must preserve.

The most complex new component is the Week view — it requires fetching 7 days of appointments, which `appointmentStore.fetchAppointments` does not yet support. This is the only new data fetch pattern needed. The Flow board is simpler: it filters `appointments[]` from the store (already loaded for the day) into four Kanban columns.

**Primary recommendation:** Build in waves — (1) WeekStrip + date navigation, (2) AppointmentDetailDrawer, (3) BookingDrawer replacing BookAppointmentModal, (4) FlowBoard, (5) WeekView, (6) public booking wizard polish. Each wave is independently deployable.

### Pattern 1: WeekStrip Navigation
**What:** Horizontal 7-day strip replacing the old prev/next/date-input row. Shows Mon-Sun labels, date numbers, and appointment count badges. Arrow buttons shift the displayed week.
**When to use:** Always visible at top of schedule page above view content.
**Key state:** `selectedDate` (existing in store) drives which day is highlighted. Week start computed from `selectedDate` using `shiftDate()` from `lib/timezone.ts`.
```typescript
// Derive week days from selectedDate
function getWeekDays(dateStr: string): string[] {
  // Find Monday of the week containing dateStr
  const d = new Date(dateStr + "T00:00:00");
  const day = d.getDay(); // 0=Sun, 1=Mon...
  const monday = new Date(d);
  monday.setDate(d.getDate() - ((day + 6) % 7));
  return Array.from({ length: 7 }, (_, i) => {
    const dd = new Date(monday);
    dd.setDate(monday.getDate() + i);
    return localDateISO(dd); // from appointmentStore
  });
}
```

### Pattern 2: Appointment Detail Drawer
**What:** Right-side slide-in panel (fixed position, z-50) showing full appointment details, patient info summary, status history, and all action buttons.
**When to use:** Triggered by clicking any appointment card in List, Timeline, Clinic, or Flow views.
**Drawer architecture decision:** Use a **single shared drawer component** with two modes (`detail` | `booking`). This avoids z-index conflicts and allows booking → detail transition on the same overlay layer.
```typescript
// Drawer state in schedule/page.tsx
type DrawerState =

  | { mode: "booking"; defaults?: BookingDefaults };

const [drawerState, setDrawerState] = useState<DrawerState>({ mode: "closed" });
```

### Pattern 3: Wait Time Indicator
**What:** Elapsed time since check-in for appointments with `arrived`, `in_pretest`, or `in_exam` status. Color-coded: amber >15min, red >30min.
**Critical:** `startTime` is appointment start, NOT check-in time. The backend `Appointment` model does NOT have a `checked_in_at` timestamp. Wait time must be computed from `startTime` as a proxy (or the badge shows time since scheduled start, which is still meaningful for a clinic).
**Decision needed at plan time:** Confirm whether backend exposes `checked_in_at`. If not, use `startTime` as proxy — document this limitation in plan.
```typescript
function getWaitMinutes(appointment: Appointment): number | null {
  if (!["arrived", "in_pretest", "in_exam"].includes(appointment.status)) return null;
  // Using startTime as proxy until checked_in_at is available
  const now = Date.now();
  const start = new Date(appointment.startTime).getTime();
  return Math.floor((now - start) / 60000);
}
```

**Column mapping:**

**30s polling:** Use `useEffect` + `setInterval` in the FlowBoard component (or page) to call `fetchAppointments(selectedDate)` every 30 seconds. Clear interval on unmount.

### Pattern 5: Week View Data Fetching
**What:** WeekView needs appointments for 7 days simultaneously. `appointmentStore.fetchAppointments` only fetches one day.
**Solution:** Add `fetchWeekAppointments(startDate: string, endDate: string)` to `appointmentStore` that calls `/api/appointments?date_from=X&date_to=Y`. This requires a new query param on the backend BFF (check if `/api/appointments/` already supports `date_from`/`date_to` — likely not).
**Alternative if backend param not available:** Fire 7 parallel `fetch` calls client-side and merge. This is simpler but less efficient. Document trade-off in plan.

### Pattern 6: Slot Picker Grid (Booking Drawer)
**What:** Visual grid of time slots for the selected date/provider. Grey = occupied, clickable = available. Hover on grey shows who occupies it.
**Source of truth:** Conflict detection already exists in `BookAppointmentModal` via `useMemo` comparing against `allAppointments` from the store. The new slot picker extends this pattern.
**Staff booking uses local appointments data** (already loaded for the day). The public booking page uses the `/api/public/booking/[slug]/availability/` endpoint.

### Pattern 7: Role-Based View Defaults
**What:** On first load (no localStorage key), default view based on role.
**Source:** `session.user.role` from Supabase JWT (via `useSession()` or `useEntitlements()`).
```typescript
function getRoleDefaultView(role: string): ViewMode {
  if (role === "receptionist" || role === "technician") return "flow";
  if (role === "doctor") return "clinic";
  return "list"; // owner, admin, default
}

const [viewMode, setViewMode] = useState<ViewMode>(() => {
  if (typeof window !== "undefined") {
    const saved = localStorage.getItem("schedule_view") as ViewMode | null;
    if (saved) return saved;
  }
  return getRoleDefaultView(session?.user?.role ?? "");
});
```

### Pattern 8: Public Booking Wizard (existing page.tsx polish)
**What:** The `app/book/[slug]/page.tsx` already exists with a 4-step wizard. Needs polish to match the 5-step spec (Type → Provider → Date/Time → Patient Info → Confirm).
**BFF routes:** All 3 public booking BFF routes already exist (`/api/public/booking/[slug]/info`, `/availability`, `/book`).
**Light/white style:** The existing page uses `var(--bg-base)` and glassmorphism CSS variables. It needs a dedicated light theme override for the public shell — use `data-theme="light"` on the root div or explicit white/gray Tailwind classes bypassing CSS variables.

### Anti-Patterns to Avoid
- **Don't fetch appointments in WeekView per-column:** Fetch the full week once, then filter client-side per day column.
- **Don't duplicate AppointmentCard action logic in FlowBoard:** Reuse the same `useScheduleActions` hook.
- **Don't open the booking drawer AND detail drawer simultaneously:** Single drawer state machine prevents this.
- **Don't use `window.setInterval` for polling:** Use `useEffect` cleanup pattern — `return () => clearInterval(id)`.
- **Don't build a custom drag-and-drop if complexity is high:** Status change buttons (e.g., "Move to In Exam") are the fallback.

## Common Pitfalls

### Pitfall 1: WeekStrip Count Badge Staleness
**What goes wrong:** Week strip shows appointment counts, but counts only update when a day is selected and appointments are fetched. Other days show stale "0" or cached counts.
**Why it happens:** `appointmentStore` only holds one day at a time.
**How to avoid:** On WeekStrip mount, prefetch all 7 days' counts OR derive counts only for the currently loaded day and show "-" for others until visited. Document which approach is chosen in plan.
**Warning signs:** Count badges showing 0 for days that have appointments.

### Pitfall 2: Wait Time Proxy Inaccuracy
**What goes wrong:** Wait time indicator shows negative or very large values because `startTime` is the scheduled appointment time, not actual check-in time.
**Why it happens:** Backend `Appointment` model has no `checked_in_at` column (confirmed from `types/appointment.ts` — not in the `Appointment` interface).
**How to avoid:** Plan must decide: (a) add `checked_in_at` field to backend/types, or (b) use `startTime` as proxy with a note, or (c) skip wait time badge until field exists. The CONTEXT.md says "elapsed time since check-in" — this implies (a) is the right answer but adds backend scope.
**Warning signs:** Negative wait times for appointments booked far in advance but checked in on time.

### Pitfall 3: Drawer Z-Index Conflicts with OverflowMenu
**What goes wrong:** `OverflowMenu` in `AppointmentCard` uses `z-50` positioning; the detail drawer also uses `z-50`. Menus render behind the drawer when it slides in.
**Why it happens:** `AppointmentCard` already has `zIndex: 50` conditional on `menuOpen` state (line 157-159).
**How to avoid:** Detail drawer should use `z-40` with a backdrop, or close any open overflow menus when the drawer opens. The safest approach: drawer uses `z-50` + backdrop at `z-40`, cards render below `z-40` when drawer is open.

### Pitfall 4: Flow Board Polling and React StrictMode
**What goes wrong:** `setInterval` fires twice immediately in StrictMode development, causing double-fetches.
**Why it happens:** React StrictMode double-invokes effects in dev. The interval is set up twice before the first cleanup.
**How to avoid:** Use a `useRef` to hold the interval ID and a `useRef(false)` to track if the component is mounted before triggering fetches.

### Pitfall 5: Public Booking Page CSS Variable Leak
**What goes wrong:** The public booking page (`app/book/[slug]/page.tsx`) uses the internal dark glassmorphism theme via `var(--bg-base)` and `var(--glass-bg)` because these variables are set globally. The light/white design requires overriding them.
**Why it happens:** Existing page uses `className="min-h-screen bg-[var(--bg-base)]"` which inherits the dark theme.
**How to avoid:** Add a `data-public-booking` attribute to the root div and define light overrides in `globals.css`, OR switch to explicit Tailwind utility classes (`bg-white`, `text-gray-900`, etc.) within the public booking page — bypassing CSS variables entirely. Prefer explicit classes since the public page is intentionally different.

### Pitfall 6: Week View Requires Backend Range Query
**What goes wrong:** `/api/appointments?date=YYYY-MM-DD` only returns one day. Week view silently shows empty columns for days other than `selectedDate`.
**Why it happens:** `appointmentStore.fetchAppointments` takes a single `date` param.
**How to avoid:** Check if FastAPI `/api/appointments/` already supports `date_from`/`date_to`. If not, plan must include a BFF + backend task to add range query before WeekView can be built. This is the only backend touch needed for the entire phase.

### Pitfall 7: ViewMode Type Extension
**What goes wrong:** Current `schedule/page.tsx` has `type ViewMode = "list" | "timeline" | "clinic"` defined inline. Extending to 5 modes requires touching multiple places.
**Why it happens:** The type is not exported from a shared location.
**How to avoid:** Extract `ViewMode` to `types/schedule.ts` or define it at the top of `schedule/page.tsx` as a single source of truth before referencing it in sub-components.

## Open Questions

1. **`checked_in_at` timestamp for accurate wait times**
   - What we know: `Appointment` type has no `checked_in_at` field; backend model needs inspection
   - What's unclear: Does the backend store check-in time anywhere (audit log? appointment update timestamp)?
   - Recommendation: Plan Wave 1 to check `backend/db/models/tenant/clinical.py` for `checked_in_at`. If absent, plan a minimal backend addition OR accept `startTime` as proxy. Do NOT silently use `startTime` without documenting the limitation.

2. **Week view range query support**
   - What we know: `/api/appointments/` only accepts `date` (single day) based on store code
   - What's unclear: Whether FastAPI route already has `date_from`/`date_to` params (not visible in BFF map)
   - Recommendation: Plan must verify FastAPI appointments route signature before building WeekView. If range not supported, add it as Wave 0 backend task.

3. **Week strip appointment counts for non-selected days**
   - What we know: Store only holds one day's appointments at a time
   - What's unclear: Whether to show counts for all 7 days (requires 7 fetches or range query) or only the selected day
   - Recommendation: Show count only for selected day initially; use range query endpoint (from Q2) to populate all 7 once it exists.

4. **Drag-and-drop on Flow board**
   - What we know: Context says "Claude's discretion — implement if reasonable complexity"
   - What's unclear: Whether `@dnd-kit` is approved as a new dependency
   - Recommendation: Plan with buttons-only fallback. Mark drag-and-drop as optional in plan tasks, gated on user approval of `@dnd-kit` dependency.
