## Summary

Phase 10.1 enriches the existing PatientInsurance model (Phase 9) with production-grade insurance fields: copay, eligibility tracking, authorization codes, and active/inactive status. The existing infrastructure (ORM model, Pydantic schemas, BFF routes, InsuranceTab component) is all in place and simply needs extension — no new tables required for the core work. The only architectural decision Claude must make is whether per-encounter auth overrides go in a new `EncounterAuth` junction table or as columns on the existing `Encounter` model.

The migration requires replacing the current hard unique constraint on `(patient_id, priority)` with a partial unique constraint scoped to `is_active = true`. PostgreSQL supports this natively but Alembic requires it be expressed via `UniqueConstraint` with a `postgresql_where` clause rather than a simple `op.create_unique_constraint`. This is the highest-risk migration step.

**Primary recommendation:** Extend ORM + schemas + BFF in a single migration wave, then layer UI changes on top. Tackle per-encounter auth as a new `EncounterAuth` table (cleaner audit trail, avoids polluting Encounter columns).

    op.add_column("patient_insurance", sa.Column("auth_number", sa.String(100), nullable=True))

### Pattern 2: Replacing Unique Constraint (CRITICAL MIGRATION STEP)
The current `uq_patient_insurance_priority` hard unique must be replaced with a partial unique:
```python
def upgrade() -> None:
    # Drop existing hard unique
    op.drop_constraint("uq_patient_insurance_priority", "patient_insurance", type_="unique")
    # Add partial unique (PostgreSQL-specific)
    op.execute(
        "CREATE UNIQUE INDEX uq_patient_insurance_active_priority "
        "ON patient_insurance (patient_id, priority) WHERE is_active = true"
    )

def downgrade() -> None:
    op.execute("DROP INDEX IF EXISTS uq_patient_insurance_active_priority")
    op.create_unique_constraint("uq_patient_insurance_priority", "patient_insurance", ["patient_id", "priority"])
```

Note: SQLAlchemy's `UniqueConstraint` with `postgresql_where` works in ORM model definition but Alembic raw `op.execute` is safer for the migration itself.

### Pattern 4: Per-Encounter Auth Override (Claude's Discretion — Recommend Junction Table)
A new `EncounterAuth` model avoids polluting the Encounter table and keeps a clean audit trail:
```python
class EncounterAuth(TimestampMixin, TenantBase):
    __tablename__ = "encounter_auth"
    __table_args__ = (
        UniqueConstraint("encounter_id", "insurance_id", name="uq_encounter_auth"),
    )
    id: Mapped[uuid.UUID] = ...
    encounter_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("encounters.id", ondelete="CASCADE"))
    insurance_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("patient_insurance.id", ondelete="CASCADE"))
    auth_number: Mapped[str | None] = mapped_column(String(100), nullable=True)
    auth_expiry: Mapped[Date | None] = mapped_column(Date, nullable=True)
    auth_services: Mapped[str | None] = mapped_column(Text, nullable=True)
```
If scope feels too large, defer EncounterAuth to a follow-on task and implement PatientInsurance-level auth first.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead |
|---------|-------------|-------------|
| Partial unique constraint | Custom application-level dedup check | PostgreSQL partial index via `op.execute` in Alembic |
| Stale date calculation | Custom date math | `differenceInDays` from `date-fns` (already a dep) or native JS `Date` arithmetic |
| Eligibility status validation | Frontend enum check | Pydantic `field_validator` + SQLAlchemy `CheckConstraint` |
| Copay formatting | Custom formatter | Intl.NumberFormat or simple template literal `$${amount}` |

## Common Pitfalls

### Pitfall 1: Hard Unique Constraint Blocks Migration
**What goes wrong:** `is_active` column added AFTER the unique constraint drop — migration fails if any patient already has duplicate priority records (impossible today, but safe ordering matters).
**How to avoid:** In a single migration: (1) add `is_active` column with `server_default='true'`, (2) drop old unique, (3) create partial index.

### Pitfall 2: `db.refresh` After `db.flush`
**What goes wrong:** Calling `db.refresh(ins)` after flush raises `MissingGreenlet` in async SQLAlchemy.
**How to avoid:** Re-fetch the record with `selectinload(PatientInsurance.payer)` after flush. This is the established pattern in this codebase (see CLAUDE.md).

### Pitfall 3: TopNav Fetches Raw snake_case
**What goes wrong:** TopNav fetches `/api/patients/{id}/insurance` directly via `fetch()` (not `apiFetch`), so response keys are snake_case (e.g., `payer_name`, not `payerName`). New fields like `copay_amount`, `eligibility_status` will also be snake_case.
**How to avoid:** Keep accessing `primaryIns.payer_name`, `primaryIns.copay_amount` (snake_case) in TopNav — do NOT use camelCase. Match the existing pattern already in use.

### Pitfall 4: Inactive Records Break Priority Uniqueness at Insert
**What goes wrong:** After partial unique is in place, creating a new active primary when an old active primary exists will violate the constraint. Need to deactivate the old one first (or the UI enforces only-one-active-per-priority).
**How to avoid:** Backend PATCH or POST for new insurance should auto-deactivate the existing active record of the same priority, or reject with a clear error message. Define this behavior explicitly in the plan.

### Pitfall 5: Schedule View Badge Requires New Data Fetch
**What goes wrong:** The schedule page doesn't currently fetch patient insurance — adding eligibility badges requires either a per-patient fetch (N+1) or insurance data embedded in the appointment list endpoint.
**How to avoid:** Embed `primary_insurance_summary` (payer short name + eligibility status) in the appointment list response payload rather than separate per-patient calls.
