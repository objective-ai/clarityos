# Phase 10.3: Error Monitoring & System Status - Context

**Gathered:** 2026-04-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Wire Sentry into both runtimes (FastAPI + Next.js) with a HIPAA-safe capture pipeline, and build an OWNER-only System Status surface inside the existing Admin page that shows live service health, the most recent errors, and uptime/deploy metadata.

Scope is pilot-launch-driven: enough observability for a solo optometrist in production, not a full SRE dashboard. Alerting beyond Sentry's built-in email, multi-channel escalation, tenant-scoped dashboards, and any proactive synthetic monitoring are explicitly out of scope for this phase.

</domain>

<decisions>
## Implementation Decisions

### Sentry scope & PHI safety
- **SDK:** `@sentry/nextjs` (wraps both client + route handlers) and `sentry-sdk[fastapi]` on the backend.
- **Environments:** prod only. Dev and Vercel preview deploys do NOT initialize Sentry — silent in those environments, zero PHI risk from fixtures/test patients.
- **Features:** errors only at launch. No performance tracing, no session replay. Transaction sample rate `0.0`. Leaves headroom to enable perf later without plan changes.
- **Release tagging:** tag events with `release = GIT_SHA` (from Vercel env + a build-time arg on FastAPI Docker image) and `environment = "production"`.
- **User context:** send `id = user.id` and `role` only — never email, name, or tenant_slug alone (tenant_slug is not PHI but combined with patient links could re-identify; keep tenant_id only).
- **PHI scrubber (deny-list):** `beforeSend` filter strips these keys anywhere they appear in event data, breadcrumbs, request params, or URL query strings:
  - Identifiers: `patient_id`, `mrn`, `dob`, `date_of_birth`, `ssn`
  - Names: `first_name`, `last_name`, `full_name`, `patient_name`
  - Contact: `phone`, `email`, `address`, `street`, `zip`, `postal_code`
  - Insurance: `insurance_number`, `member_id`, `policy_number`, `group_number`
  - Free text: `chief_complaint`, `hpi`, `assessment`, `plan`, `soap_text`, `ai_summary_text`, `note`, `notes`
- **Clinical route tagging:** FastAPI middleware adds `route_type = "clinical"` tag when the path starts with `/api/encounters`, `/api/patients`, `/api/ai-scribe`, `/api/claims`, `/api/vitals`, `/api/exam-findings`, or `/api/superbills`. For these events the entire request body is dropped (never sent to Sentry), not just scrubbed.
- **Ignore rules:** drop `ClientDisconnect`, `HTTPException(401)`, `HTTPException(403)`, and Next.js `NEXT_REDIRECT` to keep signal-to-noise high.
- **Sample rate:** errors `1.0` (capture everything), transactions `0.0`.

### Status page content
- **Panels (all three ship at launch):**
  1. **Service health** — FastAPI, Postgres, Supabase Auth shown as cards with green/amber/red dot, latency in ms, and "last checked" timestamp.
  2. **Recent errors** — last ~50 Sentry issues (title, count, first/last seen, environment, route tag) sourced from the Sentry REST API. Each row deep-links to the Sentry issue page in a new tab.
  3. **Uptime & deploy info** — 7-day uptime %, last-deploy timestamp, git commit SHA (short), environment, and "healthy since" timestamp.
- **Error source:** Sentry REST API is the single source of truth — no local `error_events` mirror table. Avoids the HIPAA risk of writing error payloads into our own DB. Auth via `SENTRY_API_TOKEN` (server-only env var, never exposed to client).
- **Health endpoint:** new `GET /system/health/` on FastAPI returns `{ api: "ok", postgres: {status, latency_ms}, supabase_auth: {status, latency_ms}, version, checked_at }`. Postgres probe = `SELECT 1`. Supabase probe = GET public `.well-known/openid-configuration` with a 2s timeout. No auth on this endpoint (it's called by the status page AND the uptime self-pinger) but rate-limited.
- **Uptime computation (Claude's discretion, committed here):** a `system_health_samples` table stores one row every 60s from a simple scheduled self-ping (the 30s client poll also writes a sample when OWNER is viewing). Uptime % = samples with `all_green = true` / total samples in the window. No UptimeRobot, no Sentry crons, no new vendor dependency.
- **Refresh cadence:** 30s auto-poll on the Status section (matches FlowBoard's pattern from 10.2); a manual "Refresh" button and a visible "Updated HH:MM:SS" timestamp sit next to the first panel.
- **Anthropic / Deepgram / Storage probes:** deferred. Anthropic is load-bearing for AI Scribe but a probe call costs tokens; adding it would need caching and is not worth the complexity this phase.

### Access & location
- **Placement:** new `"system"` key added to `SECTIONS` in `app/(tenant)/[tenant]/admin/page.tsx`. Follows the exact pattern used for `schedule` (10.4), `payers`, `compliance`. Renders a `SystemStatusSection` component.
- **Role gate:** OWNER only. New permission key `view_system_status` added to `backend/core/permissions.py` `PERMISSION_MATRIX` with `{OWNER}`.
- **Frontend guard:** `useEntitlements().has('view_system_status')` gates both the Admin sidebar entry and the direct URL (`?section=system`) — non-OWNER gets a generic "not available" message, not a 403, to avoid leaking section existence.
- **TopNav indicator:** small colored dot component (green/amber/red) shown ONLY for OWNER, placed to the left of the existing ClockInButton in `components/TopNav.tsx`. Polls `/system/health/` every 60s. Click opens `Admin > System`. Hidden for all other roles.
- **Deep-link:** `?section=system` makes the status view bookmarkable for runbooks, without a separate route tree.

### Alerting (Claude's Discretion)
- Sentry's built-in email alerts only at launch (configured at the Sentry project level, not in code). A single alert rule: "any new issue in production" → email the OWNER + Duy.
- Slack/PagerDuty/escalation policies are deferred to a later ops-focused phase.
- The System Status page itself does NOT push alerts — it's a pull-based triage surface.

### Claude's Discretion
- Exact visual treatment of the status cards (glass-card + accent dot; match Admin section typography).
- Sentry DSN naming, project slug, team assignment in Sentry org.
- Mobile/narrow-screen behavior for the TopNav dot (keep it visible, reduce padding).
- Self-pinger implementation (FastAPI startup background task vs Vercel cron → internal endpoint). Default: FastAPI `asyncio` background task every 60s, can be swapped later.

</decisions>

- **FastAPI middleware order:** PHI scrubber / Sentry init must run BEFORE auth middleware so 401s are ignored AFTER scrub. Register in `backend/main.py` immediately after app instantiation, before `include_router` calls.
- **Next.js:** `sentry.client.config.ts`, `sentry.server.config.ts`, `sentry.edge.config.ts` live at repo root. `next.config.js` wraps with `withSentryConfig`. Vercel env vars: `SENTRY_DSN`, `SENTRY_AUTH_TOKEN` (for sourcemaps), `NEXT_PUBLIC_SENTRY_DSN`, `SENTRY_ORG`, `SENTRY_PROJECT`.
- **Sentry REST API** called from the BFF proxy (server-side only) using `SENTRY_API_TOKEN`; the browser never sees the token.
- **Health endpoint unauthenticated** but rate-limited (align with `public_booking.py` rate-limit pattern).
- **TopNav rendering** depends on `useSession()` — the health dot must only render when `session.role === 'OWNER'`.

<specifics>
## Specific Ideas

- Status page should feel like a Vercel deployments page or Linear's status surface — dense but calm, glance-readable.
- Green/amber/red dots should use the same tokens as appointment wait-time indicators (10.2) so the color language is consistent: green = healthy, amber = degraded, red = down.
- Recent errors should be a table, not cards — the scanning task is "what happened, how often, when" not "beautiful per-error detail." Detail lives in Sentry itself.
- The status page is an internal tool; it is allowed to be plainer than public-facing surfaces.

</specifics>

<deferred>
## Deferred Ideas

- **Multi-channel alerting** (Slack, SMS, PagerDuty, escalation rules) — future ops phase. Sentry email only at launch.
- **Anthropic / Deepgram / Storage health probes** — add when those dependencies become user-visible or load-bearing for the pilot.
- **Tenant-scoped error dashboards** — show each clinic their own errors. Needed only when ClarityOS serves multiple tenants in prod.
- **Error trend sparkline (24h chart)** — declined from the launch panels. Revisit after pilot if triage takes too long.
- **Session replay** — requires Sentry BAA scope verification and aggressive input masking. Revisit post-pilot.
- **Performance tracing** — transaction sample rate is `0.0` at launch. Turn on once error volume is controlled.
- **Local `error_events` mirror table** — rejected this phase due to PHI risk; reconsider only if Sentry availability becomes an issue.
- **Structured logging / log aggregation (Loki, Datadog)** — separate concern from error capture; out of scope.

</deferred>
