### 1. Multi-Tenant SaaS Architecture

Since you are building a SaaS for multiple optometry practices, data isolation and security (especially for HIPAA compliance) are the top priorities.

* **Database Strategy:** I strongly recommend using a **PostgreSQL** database with a **Schema-per-Tenant** architecture.
* *Why:* Instead of mixing all patient data in the same tables and relying solely on a `tenant_id` column (which risks accidental data leaks), or spinning up a whole new database for every clinic (which is a nightmare to scale and maintain), a schema-per-tenant model gives every clinic its own isolated schema within a single database. * **Authentication & RBAC:** We will need strict Role-Based Access Control (RBAC). A doctor, an optometric technician, and a front-desk receptionist will all need vastly different permissions within a single clinic's tenant.

You want something future-proof, easy to scale, and developer-friendly. Here is a highly effective, modern stack for this type of system:

* **Backend:** Building the core logic in **Python** using a modern framework like **FastAPI** or **Django** is an incredibly strong choice. Python is highly readable, universally supported, and handles complex relational data beautifully. Furthermore, if you plan to introduce AI features later (like automated charting or diagnostic analysis), Python is the native language for those ecosystems.
* **Frontend:** A component-based framework like **React** (specifically Next.js) is the industry standard for complex SaaS dashboards. It allows you to build highly interactive, responsive interfaces for the doctors.
* **Infrastructure:** Containerizing the application using Docker and hosting it on AWS or Google Cloud via managed container services (like AWS ECS or Google Cloud Run) will allow the system to scale automatically as you add more clinics.

Spot on. If monetization relies on tiered access and premium add-ons, "entitlement management" needs to be baked into the foundational architecture from day one. Trying to shoehorn feature flags into a mature codebase later is a nightmare.

Since AI features (like automated charting, predictive patient scheduling, or diagnostic trend analysis) are incredibly resource-heavy, gating them not only drives revenue but also protects your infrastructure costs.

Here is how we should architect the system to handle tiers and a la carte add-ons elegantly:

### 1. The Entitlement Data Model (Database Level)

Instead of hardcoding boolean flags like `has_ai_feature = True` on the tenant table, we need a flexible, relational entitlement system.

* **Tiers:** A `Tenant` belongs to a `SubscriptionPlan` (e.g., Core, Plus, Premium). Each plan is mapped to a set of default `Features`.
* **Add-ons:** A `TenantAddon` table acts as a join table between a `Tenant` and specific individual `Features` (e.g., "AI Scribe", "Advanced Trend Analytics").
* This way, a clinic on the "Core" plan can still purchase the "AI Scribe" as a standalone add-on without upgrading their entire tier.

### 2. The Middleware / Gateway Layer (Backend Security)

We never trust the frontend to enforce gating. In our Python backend (like FastAPI or Django), we will build an authorization middleware.

* **Decorators/Dependencies:** We can write a custom decorator for our API routes. For example, the endpoint to generate an AI summary would look something like `@requires_entitlement('ai_charting')`.
* If a tenant makes a request to this endpoint and lacks the entitlement, the API immediately throws an HTTP 403 (Forbidden) error.

### 3. The AI Processing Architecture (Resource Management)

Because AI requests take time to generate and cost money (LLM token usage), we have to decouple them from the main clinical workflow.

* **Asynchronous Workers:** When a doctor clicks "Generate AI Chart," the API should just return a "Processing" status and hand the job off to an asynchronous message queue (like Celery with Redis).
* **Agentic Workflows:** For complex premium features—like analyzing historical patient data across Excel exports to spot financial or clinical trends—you might want to architect an internal AI agent orchestrator. Using isolated Python workers, or even integrating a node-based workflow engine like n8n on the backend, allows you to securely chain these complex AI tasks together without slowing down the core web application.

### 4. Frontend UX & Payload (The User Experience)

The React/Next.js frontend needs to know what the user is allowed to do so it can render the UI appropriately.

* **The JWT / Session Payload:** When a user logs in, the backend evaluates their tenant's tier and add-ons, and attaches an array of `entitlements` (e.g., `['basic_exam', 'billing_export', 'ai_scribe']`) to their session token.
* **Upselling:** The frontend reads this array. If the user doesn't have `ai_scribe`, the UI doesn't hide the AI button—it shows it with a lock icon. Clicking it triggers an upsell modal: *"Upgrade to Premium or add the AI Scribe module to automate your charting."*

### 5. Billing Sync (The Source of Truth)

We will likely integrate with a platform like Stripe or Chargebee. We'll set up webhooks so that the moment a clinic's credit card is successfully charged for an add-on, Stripe pings our backend, and our database automatically grants the entitlement.

Designing the database structure first is the absolute best move. If you get the data models right, the API and frontend will naturally fall into place. If you get them wrong, you'll be writing messy, complicated code to patch the gaps later.

Since we agreed on a **Schema-per-Tenant PostgreSQL** architecture, our database will actually be split into two distinct areas: the **Public Schema** (which manages the SaaS overhead) and the **Tenant Schema** (the actual clinic data, duplicated for every clinic that signs up).

Here is the blueprint for the MVP database structure.

### 1. The Global SaaS Layer (Public Schema)

This schema sits above all the clinics. It handles authentication, billing, and routing users to their correct clinic database.

| Table | Core Columns | Description |
| --- | --- | --- |
| **`tenants`** | `id`, `name`, `schema_name`, `status`, `created_at` | The master list of clinics. `schema_name` points to their isolated database schema (e.g., `clinic_1042`). |
| **`subscription_plans`** | `id`, `name`, `price`, `base_features_jsonb` | e.g., "Core", "Premium". |
| **`tenant_addons`** | `id`, `tenant_id`, `feature_name`, `active` | This maps our premium AI features (like `ai_scribe`) to specific clinics. |
| **`global_users`** | `id`, `email`, `password_hash`, `tenant_id` | Handles login. Once authenticated, the system uses `tenant_id` to route them to the right schema. |

---

### 2. The Patient & Scheduling Module (Tenant Schema)

Everything from this point down lives *inside* an individual clinic's isolated schema.

| Table | Core Columns | Description |
| --- | --- | --- |
| **`patients`** | `id`, `first_name`, `last_name`, `dob`, `sex`, `contact_info_jsonb` | Core demographics. We use JSONB for contact info to easily store multiple phone numbers/emails without extra tables. |
| **`staff`** | `id`, `global_user_id`, `role`, `first_name`, `last_name` | Maps the global user to their role in this specific clinic (`doctor`, `technician`, `admin`). |
| **`appointments`** | `id`, `patient_id`, `staff_id` (Provider), `start_time`, `end_time`, `status` | Status can be `scheduled`, `arrived`, `in_exam`, `completed`. |

---

### 3. The Clinical Encounter Module (The Core MVP)

An "Encounter" is a single visit. Optometry data is highly structured, but exam templates change. We will use a hybrid approach: strict relational columns for critical medical data (like prescriptions) and flexible `JSONB` columns for exam notes.

| Table | Core Columns | Description |
| --- | --- | --- |
| **`encounters`** | `id`, `patient_id`, `staff_id`, `appointment_id`, `date`, `chief_complaint`, `ai_summary_text` | The master record for the visit. Notice the `ai_summary_text` column ready for our premium feature. |
| **`vitals_and_pretest`** | `id`, `encounter_id`, `blood_pressure`, `iop_od` (Right Eye Pressure), `iop_os` (Left Eye Pressure) | Basic stats taken by the technician before the doctor comes in. |
| **`diagnoses`** | `id`, `encounter_id`, `icd10_code`, `description`, `eye_affected` | `eye_affected` is an enum: `OD` (Right), `OS` (Left), or `OU` (Both). Crucial for medical billing later. |

#### The Refraction Table (Strictly Relational)

This is the most important table in optometry. You cannot use flexible JSON here because you will eventually need to query, graph, and analyze prescription changes over time.

There are usually multiple refractions per visit (the patient's old glasses, the autorefractor machine reading, and the final prescription the doctor decides on).

| Table: `refractions` | Description |
| --- | --- |
| `id`, `encounter_id` | Primary keys and relations. |
| `type` | Enum: `habitual` (old glasses), `auto` (machine), `manifest` (doctor's exam), `final` (the actual prescription given). |
| `od_sphere`, `od_cylinder`, `od_axis`, `od_add` | **Right Eye (Oculus Dexter):** Mathematical values (e.g., Sphere: -2.25, Cyl: -1.00, Axis: 090). Stored as decimals. |
| `os_sphere`, `os_cylinder`, `os_axis`, `os_add` | **Left Eye (Oculus Sinister):** Same parameters for the left eye. |
| `pd_distance`, `pd_near` | Pupillary Distance (needed to physically make the glasses). |

#### The Exam Findings Table (The JSONB Trick)

Instead of creating 20 different tables for the Cornea, Retina, Macula, Lens, etc., we use one table with a JSONB column.

| Table: `exam_findings` | Description |
| --- | --- |
| `id`, `encounter_id` | Primary keys. |
| `category` | Enum: `slit_lamp_anterior` (front of eye), `fundus_posterior` (back of eye). |
| `details_jsonb` | A flexible payload. E.g., `{"cornea_od": "clear", "cornea_os": "mild scarring", "lens_od": "trace cataract"}`. |

*Why this works:* Optometrists all document slightly differently. By keeping the exam findings in a JSONB column, our React frontend can generate highly customizable, dynamic forms for the doctors without us having to alter the database schema every time a doctor wants a new checkbox.

Moving straight into the API layer is the logical next step. Now that we have a solid data foundation with our schema-per-tenant PostgreSQL database, we need a robust, secure way for the React frontend to communicate with it.

Given that we are building this in Python, **FastAPI** is the absolute best choice for our backend framework. It is asynchronous by default (which we need for our AI tasks), automatically generates OpenAPI (Swagger) documentation, and enforces strict data validation using Pydantic models. Claude is exceptionally good at writing Pydantic models if you give it the database schema.

Here is how we should architect the API layer for our Optometry EHR.

### 1. The Tenant Routing Middleware (The Gatekeeper)

Before any API endpoint does its job, we need to ensure the user is only querying their specific clinic's data.

* **The Request:** The React frontend sends a request with a JWT (JSON Web Token) in the Authorization header.
* **The Middleware:** We will build a FastAPI dependency (middleware) that intercepts every request. It decodes the JWT, extracts the `tenant_id`, and grabs the user's role and entitlements.
* **The Database Connection:** The middleware then dynamically sets the PostgreSQL `search_path` to that specific clinic's schema (e.g., `SET search_path TO clinic_1042`). This guarantees that even if a developer makes a mistake in a SQL query, it is physically impossible for the query to return another clinic's patient data.

### 2. API Namespace Structure

To keep the codebase manageable, we should version our API and group our endpoints by domain. Here is the high-level RESTful structure:

#### A. Global & Authentication (`/api/v1/global`)

These endpoints hit the **Public Schema** and manage SaaS-level operations.

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/global/auth/login` | `POST` | Authenticates the user, determines their clinic, and returns the JWT with their entitlements payload. |
| `/global/tenants/{id}/billing` | `GET/POST` | SaaS billing portal integration (Stripe webhooks, subscription tier management). |

#### B. Patient Management (`/api/v1/patients`)

These endpoints interact exclusively with the **Tenant Schema**.

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/patients` | `GET` | Search for patients (paginated). |
| `/patients` | `POST` | Create a new patient record. |
| `/patients/{id}` | `GET` | Retrieve the patient's full dashboard (demographics, past visits). |

#### C. The Clinical Encounter (`/api/v1/encounters`)

This is the workhorse of the application. We map these directly to the clinical tables we designed earlier.

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/encounters` | `POST` | Initializes a new visit when the patient walks into the exam room. |
| `/encounters/{id}/vitals` | `PUT` | The technician saves the intraocular pressure and blood pressure. |
| `/encounters/{id}/findings` | `PATCH` | The doctor saves the JSONB payload of their slit-lamp and retina exam notes. |
| `/encounters/{id}/refractions` | `POST` | Logs a new prescription (habitual, auto, or final). |
| `/encounters/{id}/diagnoses` | `POST` | Attaches an ICD-10 medical billing code to the visit. |

### 3. Asynchronous AI Endpoints (The Premium Features)

Because AI generation (like summarizing a visit or generating a referral letter) takes 5 to 15 seconds, we cannot use standard synchronous requests, or the doctor's UI will freeze.

* **Triggering the Job:** `POST /api/v1/encounters/{id}/ai-scribe`
* The frontend hits this endpoint. The API checks the user's entitlements.
* If authorized, the API packages the encounter data and drops it into an asynchronous message queue (like Redis/Celery).
* The API immediately returns an `HTTP 202 Accepted` with a `job_id`.


* **Polling or WebSockets:** The React frontend can either poll a status endpoint (`GET /api/v1/jobs/{job_id}`) every 2 seconds, or we can open a WebSocket connection so the backend can push the completed AI summary directly into the doctor's text box the moment it is ready.

### 4. Data Validation (Pydantic)

This is where FastAPI shines. We will define strict Pydantic schemas for everything. For example, when the doctor submits a final prescription to `/encounters/{id}/refractions`, the API automatically validates that the `axis` is a number between 1 and 180. If it's 185, the API immediately rejects it with a clean error message before it ever touches the database.

Excellent choice. The frontend is where an Electronic Health Record (EHR) system lives or dies. Optometrists are notorious for hating software that requires too many clicks or forces them to take their hands off the keyboard during a refraction.

If we design this React/Next.js architecture correctly, the UI will feel lightning-fast, and we can seamlessly integrate those premium AI upsells right into their natural workflow.

Here is how we should architect the frontend repository and the core component hierarchy.

### 1. The Next.js Folder Architecture (App Router)

Using the modern Next.js App Router gives us a fantastic way to separate the public SaaS landing pages from the secure, multi-tenant application.

* **`app/(public)/`**: The marketing pages, pricing, and the main login screen.
* **`app/(auth)/`**: The secure portal. Once logged in, the system checks their `tenant_id` and routes them appropriately.
* **`app/(tenant)/[tenantId]/`**: The core application. Everything inside this route automatically has the context of the specific clinic.
* `/schedule`: The daily calendar view.
* `/patients/[patientId]`: The patient's historical dashboard.
* `/encounter/[encounterId]`: The active exam room interface.



### 2. Core Clinical Components (The Exam Room)

The `Encounter` view is the most critical page in the entire EHR. Instead of forcing the doctor to click through multiple separate pages, we should build a unified, single-page dashboard using modular React components.

Here are the primary components we need to plan for:

* **`<PatientStickyHeader />`**: A banner fixed to the top of the screen showing Name, DOB, Age, and critical medical alerts (e.g., "Allergic to Penicillin", "Glaucoma Suspect").
* **`<PastHistorySidebar />`**: A collapsible left-hand sidebar that allows the doctor to quickly reference the patient's previous prescriptions and past exam findings without leaving the current screen.
* **`<RefractionGrid />`**: This is the most mathematically complex UI element.
* It needs to be a highly optimized data grid for Right Eye (OD) and Left Eye (OS).
* **Crucial UX:** It must support rapid keyboard navigation (Tab and Arrow keys). Doctors type prescriptions like `-2.25 -1.00 090` rapidly. If they have to use a mouse to click into every single input box, they will hate the system.


* **`<DynamicExamFindings />`**: This component interacts with our backend `JSONB` structure. It renders an accordion or tabbed list (Cornea, Lens, Retina). We can build it to be customizable per tenant, so Clinic A can have different checkboxes than Clinic B.

### 3. Integrating the Premium Features (Entitlement UX)

This is where our gating strategy from earlier pays off on the frontend. We will create a custom React Hook, something like `useEntitlements()`, which checks the user's JWT payload.

* **`<AiScribeWidget />`**: A floating action button or a slide-out panel.
* If `useEntitlements().has('ai_scribe')` is true, clicking it opens a WebSocket connection that streams the AI-generated chart notes directly into their text boxes in real-time.
* If false, clicking it triggers an **`<UpsellModal />`** detailing the time they could save by upgrading their tier.


* **`<AdvancedAnalyticsDashboard />`**: Rendered in the main navigation, but locked with a badge if they are on the basic tier.

### 4. State Management (Handling Unsaved Data)

An exam can take 20 minutes. If the clinic's Wi-Fi drops, the doctor cannot lose their refraction data or exam notes.

* **Local State (Zustand or React Context):** We will keep the "Active Encounter" state in memory on the frontend.
* **Auto-Save (Debouncing):** We will build a custom hook that listens for changes in the exam form. Every time the doctor stops typing for 2 seconds (a "debounce"), the frontend silently fires a `PATCH` request to our FastAPI backend to save the draft.
* **Optimistic UI:** When the doctor clicks a checkbox, the UI instantly shows it as checked, while the network request happens in the background. This makes the software feel incredibly fast.
