AI Scribe Validation Station — Architecture Approaches

Choose how to build the split-pane reviewer on top of the existing AI Scribe

A

Extend Existing Architecture (Recommended)

Keep useAiScribe.ts hook + inline AiScribeWidget for generation.

Add a new ValidationStationModal component that receives SOAP text + structured data.

Upgrade the Anthropic system prompt with confidence scores + better optometry routing.

Reuse existing store dispatch logic from the current accept handler.

Pros

  • Minimal code churn — extends, doesn't replace
  • Existing streaming + accept logic stays intact
  • One new component + prompt upgrade

Cons

  • Field editing in modal needs new local state management
  • Must bridge between modal edits and store dispatch
B

New Dedicated Pipeline

New useScribeReview.ts hook managing validation state (editing, per-field accept/discard).

New ValidationStation/ component directory with specialized sub-components.

Supports partial acceptance — accept some fields, discard others individually.

Pros

  • Clean separation of generation vs review concerns
  • Per-field accept/discard granularity
  • Purpose-built state management

Cons

  • More code to write and maintain
  • Duplicates some store dispatch logic
  • Higher complexity for v1
C

Minimal Viable Upgrade

Only upgrade the Anthropic prompt (confidence + optometry routing).

Simple modal: SOAP on left, raw JSON preview on right. No field-specific rendering.

"Edit" just closes the modal and scrolls to the relevant encounter section.

Pros

  • Fastest to build — days not weeks
  • Prompt improvements ship immediately
  • Low risk, easy to iterate

Cons

  • No inline editing — doctor bounces between modal and encounter page
  • No refraction grid, ICD-10 pills, or confidence badges in UI
  • Doesn't deliver the "Validation Station" vision
